## Требования

- JDK 21
- Android SDK Platform 37, Build Tools 36.0.0
- Android NDK `27.2.12479018` и CMake `3.22.1` (для нативного конвертера DSD)
- Устройство или эмулятор `arm64-v8a`, чтобы запускать; приложение несёт только 64-битную ARM-библиотеку

В `BUILD_LOCAL.md` есть команды `sdkmanager` и скрипт сборки при малом объёме памяти.

## Сборка

Из корня репозитория:

```sh
./gradlew :app:assembleDebug     # app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:assembleRelease   # app/build/outputs/apk/release/app-release.apk
```

(`gradlew.bat` в Windows.)

Сборка **debug** неоптимизирована и заметно медленнее; оценивая скорость, используй сборку **release**. Она проходит
через R8 (сжатие кода и ресурсов, правила в `app/proguard-rules.pro`) и именно она публикуется. Релизная сборка
подписывается стандартным ключом отладки Android, если не настроен свой (см. [Подпись](#подпись)), поэтому ставится на
твоё устройство, но не поверх официального релиза.

Lint отключён для релизных сборок (`lint { checkReleaseBuilds = false }`), чтобы он не мог их уронить.

## Тесты

```sh
./gradlew :app:testDebugUnitTest
```

Только JVM-юнит-тесты; что они покрывают, см. в [architecture.ru.md](architecture.ru.md#тесты). Тестов на устройстве
нет: поведение интерфейса, сервиса плеера и JNI-конвертера проверяется вручную на телефоне.

Релизную сборку стоит поставить и опробовать перед выпуском, потому что R8 может сломать то, что работает в debug
(например, JNI-класс `NativeDsdDecoder`, который явно сохранён в `proguard-rules.pro`).

## Непрерывная интеграция

`.github/workflows/build.yml` запускается на push в `main`, pull request'ы, теги `v*` и ручной запуск. Новый запуск на
том же ref отменяет старый.

**Задача `build`** (Ubuntu 24.04, JDK 21, Android SDK 37 / build-tools 36.0.0 / NDK / CMake как выше):

1. Восстанавливает ключ подписи из секретов репозитория, если они есть.
2. Запускает `./gradlew :app:testDebugUnitTest :app:assembleRelease`.
3. Называет APK `FeatherW8-v<версия>-arm64-v8a.apk`, беря версию из `appVersionName`.
4. Печатает SHA-256 сертификата подписи, чтобы его можно было сравнить между сборками.
5. На теге проверяет, что тег равен `v<appVersionName>`.
6. Загружает APK как артефакт (и отчёты тестов, если что-то упало).

**Задача `release`** только для тегов `v*` и только после успеха `build`: создаёт релиз на GitHub с APK и, в качестве
заметок, содержимым `docs/release-notes/<тег>.md` (или сгенерированными заметками, если файла нет).

Pull request'ы из форков секретов не получают; их сборки переходят на debug-ключ и всё равно проходят.

Чтобы получить APK любого запуска на свою машину:

```sh
gh run list --branch <ветка> --limit 1
gh run download <id-запуска> --dir apk
```

## Подпись

Официальные релизы подписываются ключом проекта. Его **нет в репозитории**.

| Где | Что |
|---|---|
| Секрет репозитория `FEATHERW8_KEYSTORE_BASE64` | Файл хранилища ключей в base64 |
| Секрет репозитория `FEATHERW8_KEYSTORE_PASSWORD` | Его пароль (пароль ключа тот же, как в хранилище PKCS12) |
| Алиас ключа | `featherw8` (задан в workflow) |

Хранилище — файл PKCS12 с ключом RSA 4096, действующим 100 лет. SHA-256 отпечаток его сертификата:
`5d82000615449058440720287495cee52bcabdb058c1d6051518154ab1ea13ac` (журнал сборки печатает его каждый раз).

**Храни резервную копию хранилища и его пароля вне этой машины.** Android ставит обновление только поверх
приложения, подписанного тем же ключом. Если ключ потерян, обновиться на месте не сможет никто: пользователям придётся
удалять приложение (и терять данные), а само приложение с тех пор будет подписано новым ключом. Сменить ключ без
такого разрыва нельзя.

Gradle берёт ключ из переменных окружения, поэтому тот же механизм работает и локально:

```text
FEATHERW8_KEYSTORE=<путь к .jks>
FEATHERW8_KEYSTORE_PASSWORD=<пароль>
FEATHERW8_KEY_ALIAS=<алиас>
```

Без `FEATHERW8_KEYSTORE` сборки используют стандартный ключ отладки.

Чтобы создать новый ключ (для нового проекта или форка, которому нужен свой):

```sh
keytool -genkeypair -keystore featherw8.jks -storetype PKCS12 -alias featherw8 \
        -keyalg RSA -keysize 4096 -validity 36500 -storepass <пароль> -keypass <пароль> \
        -dname "CN=FeatherW8, O=<ты>"
base64 -w0 featherw8.jks | gh secret set FEATHERW8_KEYSTORE_BASE64
gh secret set FEATHERW8_KEYSTORE_PASSWORD
```

## Версии

Версии вида `MAJOR.MINOR.PATCH`, выбираются по тому, насколько изменение важно тому, кто обновляется:

- **PATCH** (1.4.0 → 1.4.1): только исправления ошибок; переучиваться не нужно.
- **MINOR** (1.4.0 → 1.5.0): новые возможности или заметные изменения поведения, при которых данные пользователя
  продолжают работать.
- **MAJOR** (1.x → 2.0.0): изменение, которое может сломать существующие данные, или удаление возможности.

Версия записана **один раз**, в `app/build.gradle.kts`:

```kotlin
val appVersionName = "1.4.1"
```

а `versionCode` вычисляется из неё (`1.4.1` → `10401`, то есть `major × 10000 + minor × 100 + patch`), поэтому они не
могут разойтись, а код всегда растёт вместе с версией. Бейдж версии в README обновляется вручную с каждым релизом.

## Выпуск релиза

1. Сделай изменение в ветке и открой pull request. CI должен быть зелёным.
2. В том же pull request'е:
   - подними `appVersionName`, как описано выше;
   - добавь `docs/release-notes/v<версия>.md` (несколько пунктов, затем строка «APK notes»);
   - добавь тот же текст в [`CHANGELOG.md`](../CHANGELOG.md);
   - обнови бейджи в README (`README.md`, `README.ru.md`) и всё остальное, что затрагивает изменение.
3. Поставь APK из запуска CI этого pull request'а на телефон и опробуй его.
4. Влей. В истории используются обычные merge-коммиты.
5. Поставь тег на merge-коммит и запушь его:

   ```sh
   git switch main && git pull --ff-only
   git tag -a v<версия> -m "FeatherW8 <версия>"
   git push origin v<версия>
   ```

6. Запуск по тегу собирает, подписывает и публикует релиз. Проверь, что в релизе есть APK, правильные заметки и что
   в журнале стоит «Signing with the project key» с привычным отпечатком.

Тег должен быть равен `v` плюс `appVersionName`, иначе сборка остановится.

## Работа над изменением

В истории коммитов используются обычные префиксы: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `ci`, `build`,
`style`, `chore`. Несколько привычек, которые себя оправдали:

- **Пиши «почему»** в сообщении коммита, а не только «что»; несколько исправлений здесь вышли из неочевидной причины.
- **Предпочитай чистые функции** для всего, где есть крайние случаи, и тестируй их на JVM (`ListEdits`,
  `ActualPlayCounter`), раз тестов на устройстве нет.
- **Держи состояние Compose наверху, а экраны без состояния**; новые экраны и диалоги принимают значения и колбэки.
- **Проверяй на устройстве**, релизной сборкой, всё, что затрагивает воспроизведение, жесты, уведомление или R8.
